# Comprehension test plan — `understand`, then `state` with intents

Hands-on verification of the two deterministic comprehension surfaces and the opt-in intent
layer. Written **2026-08-14 against 3.18.0**.

**Every command below was run and its output captured** — the "expect" lines are real output,
not intentions. Numbers marked *(repo-dependent)* change with the repository; numbers without
that marker are properties that must hold anywhere.

Companion to [`cli-test-plan.md`](cli-test-plan.md) (the broad CLI sweep) and
[`pkg-accuracy-test-plan.md`](pkg-accuracy-test-plan.md) (the accuracy oracles). This one
covers `understand` → `state` → `--intents` deeply.

> **Two known failures are baked into this plan, at §5 and §9.** They are not hypotheticals —
> both reproduced on every attempt. Do not treat a matching failure as your setup being broken.

## 0. Prerequisite — use the right `orchestrator`

The most likely reason a command fails is that your shell resolves a different, older install.

```bash
command -v orchestrator && orchestrator understand --help | grep -c intents
```

If that prints a path outside this repo's `.venv`, or prints `0`, pick one:

```bash
export SPINE=/Users/falcon/projects/ai/spine/.venv/bin/orchestrator
```

Every command here uses `$SPINE`.

## 1. Target — test against a clone, not your working tree

`understand` **writes `episteme/` into the target repo** by default. Use a clean clone at a
fixed tag so results are comparable and your working tree is never touched.

```bash
mkdir -p /tmp/spine-comprehension && cd /tmp/spine-comprehension
git clone -q /Users/falcon/projects/ai/spine spine && git -C spine checkout -q v3.18.0
git -C spine rev-parse --short HEAD && git -C spine status --porcelain | wc -l
```

Expect `92d2947` and `0` — a **clean tree**, which matters: per invariant 8 the commit-keyed
cache is only trusted on a clean tree, so a dirty clone silently re-extracts every run and
your timings become meaningless.

### 1b. …or run against your live working tree — three things change

Testing `/Users/falcon/projects/ai/spine` directly is fine, but the plan's captured numbers
were taken at the `v3.18.0` tag on a clean clone. Adjust for:

**① `episteme/` is tracked here — 91 files. Never run `understand .` without `--out`.**

```bash
git ls-files episteme | wc -l      # 91
```

A bare `understand .` **overwrites 91 tracked files** in your working tree. CLAUDE.md is
explicit that `episteme/` is never committed — it is regenerated by
[`episteme.yml`](../../.github/workflows/episteme.yml) after merge, and CI fails any PR
carrying it. Always write elsewhere:

```bash
$SPINE understand . --out /tmp/ep-a          # safe
```

If you do overwrite it: `git checkout -- episteme/` restores it.

**② The install is editable, so "3.18.0" is not the tag.**

```bash
.venv/bin/python -c "import importlib.metadata as d; print(d.distribution('synaptixs-spine').read_text('direct_url.json'))"
# {"url":"file:///Users/falcon/projects/ai/spine","dir_info":{"editable":true}}
```

You are running `develop` plus your uncommitted changes; the version string only moves at a
release. Expect **11912** grounded nodes here vs **11888** at the tag — a difference, not a
failure.

**③ A dirty tree makes §4 fail and §9 meaningless.** Observed on `develop` today:

```
[understand] brownfield — 11912 grounded nodes
episteme is stale — 3 out of date.
  out of date: README.md
  out of date: architecture.md
  out of date: modules/orchestrator.pkg.persistence.md
```
(exit `1`)

This is **not** a defect — it is the CLAUDE.md gotcha firing exactly as documented. Two
untracked files under `docs/specs/` are ingested as `Doc` nodes whether or not git tracks
them, so the rendered bank no longer matches the committed one. The third file is the tell:
`pkg-accuracy-gaps.md` cites `pkg/persistence.py`, which creates a `MENTIONS` edge and changes
that module's page.

Commit the untracked docs first, or run §4 against a clean clone. And note the cache is
distrusted while the tree is dirty, so every run re-extracts — do not compare §9 timings
against a dirty tree.

> **Capture the exit code without a pipe.** `… --check | tail` reports `tail`'s status, not
> the command's. Use `$SPINE understand . --check >/dev/null 2>&1; echo $?` — this bit me
> twice while writing this plan.

## 2. `understand` — the first build

Write to an explicit `--out` so the committed `episteme/` stays untouched and you can diff runs.

```bash
$SPINE understand spine --out ep-a
```

Expect a JSON summary ending in `"grounded_nodes": 11888` *(repo-dependent)* and:

```bash
find ep-a -type f | wc -l          # 91  (repo-dependent)
ls ep-a
```

`README.md`, `architecture.md`, `tech-context.md`, `symbol-index.md`, `progress.md`,

**What to look for.** Open `ep-a/architecture.md` and confirm the graph-size line reflects
real extraction, and that `ep-a/symbol-index.md` names symbols you recognise. This is the
"code-true" claim — every line should be traceable to a file, never inferred from a path.

## 3. Determinism — the property the whole thing rests on

Invariant 2: *same code in → same output out.* This is why `understand` is trusted, and it is
the single most valuable thing to verify.

```bash
$SPINE understand spine --out ep-b
diff -rq ep-a ep-b && echo "PASS — byte-identical"
```

**Expect `PASS`.** ✅ Verified: identical across runs.

If this ever fails, stop and treat it as a release blocker — `understand --check` in CI is
only meaningful while this holds.

## 4. `--check` — provable currency, not hopeful currency

```bash
$SPINE understand spine --check ; echo "exit=$?"
```

Expect ✅:

```
[understand] brownfield — 11888 grounded nodes
episteme is current — it matches the code at commit 92d2947254a8.
exit=0
```

`--check` writes nothing. Verify that:

```bash
git -C spine status --porcelain | wc -l    # still 0
```

**Negative case** — make it disagree, and confirm it actually catches it:

```bash
echo 'def brand_new_function_xyz(): pass' >> spine/src/orchestrator/cli.py
$SPINE understand spine --check ; echo "exit=$?"
git -C spine checkout -- src/orchestrator/cli.py
```

Expect a **non-zero exit** and a named list of stale files. Observed ✅:

```
  out of date: architecture.md
  out of date: areas/orchestrator.cli.md
  out of date: conventions.md
  out of date: modules/orchestrator.cli.md
  out of date: symbol-index.md
Regenerate with `orchestrator understand .` and commit the result.
exit=1
```

A `0` here would mean CI's currency gate is decorative. Note the tree is dirty for this run,
so it re-extracts rather than using the cache — it will be slower.

## 5. `state` — the two lenses, and a **known determinism failure**

```bash
$SPINE state spine --lens developer --no-timestamp > st-dev.md
$SPINE state spine --lens stakeholder --no-timestamp > st-stake.md
wc -l st-dev.md st-stake.md
```

Expect ~237 lines for developer *(repo-dependent)*. Read both: the stakeholder lens must be
plain language with no symbol ids leaking through.

Always pass `--no-timestamp` when diffing — otherwise the generated-at time guarantees a diff.

### 5.1 ⚠️ KNOWN FAILING — `state` is not deterministic

```bash
for i in 1 2 3 4 5; do $SPINE state spine --no-timestamp > run$i.md; done
md5 -q run*.md | sort | uniq -c
```

**Expect 2–3 distinct hashes across 5 identical runs.** Observed: `3`, `1`, `1`.

This violates invariant 2. Find the varying line:

```bash
diff run1.md run2.md
```

Observed — the `scripts/` component list reorders entries that **tie** on their counts:

```
- **scripts/** — … `scripts.security_verify` (0 types, 12 fns), `scripts.security_sweep` (0 types, 12 fns), …
- **scripts/** — … `scripts.security_sweep` (0 types, 12 fns), `scripts.security_verify` (0 types, 12 fns), …
```

**Root cause**, [`knowledge/current_state.py:647`](../../src/orchestrator/knowledge/current_state.py):

```python
areas = set(s.area_types) | set(s.area_funcs)      # set iteration order is per-process random
for a in sorted(areas, key=lambda a: ...score..., reverse=True):   # stable sort keeps that order for ties
```

Python randomizes string hashing per process, so the set yields a different order each run;
`sorted()` is stable, so equal-scoring areas inherit it. Confirm the diagnosis — pinning the
seed must make it stable:

```bash
for i in 1 2 3 4 5; do PYTHONHASHSEED=0 $SPINE state spine --no-timestamp | sed -n '42p' | md5; done
```

Expect **5 identical hashes**. ✅ Verified.

`PYTHONHASHSEED=0` is the workaround for any diffing you do today. The fix is a total sort
key (append the area name as a tiebreaker).

### 5.2 The shareable report

```bash
$SPINE state spine --no-timestamp --out report.html
grep -c 'src="http\|href="http.*\.css\|/static/' report.html
```

Expect **`0`** ✅ (verified — 25 KB, self-contained). Invariant 5 says a shared artifact inlines
everything and fetches nothing. Open it and confirm it renders standalone.

## 6. `--intents` on `understand` — what actually changes

The help text says *"Opt-in — nothing renders these facts yet."* This section is a falsifiable
test of exactly that claim, not a tour.

```bash
$SPINE understand spine --intents --out ep-intents
diff -rq ep-a ep-intents
```

Observed — **two files differ, and only count lines within them**:

```
Files ep-a/README.md and ep-intents/README.md differ
Files ep-a/architecture.md and ep-intents/architecture.md differ
```

```bash
diff ep-a/architecture.md ep-intents/architecture.md
```

```
< **Graph size:** 12471 nodes · 34414 edges — … · 71 endpoints · 7 entitys.
> **Graph size:** 12505 nodes · 35733 edges — … · 71 endpoints · 34 intents · 7 entitys.
```

So `--intents` added **+34 Intent nodes and +1319 SERVES edges** *(repo-dependent)*, and the
entire rendered consequence is the word `34 intents` in two size lines.

**The check that matters** — is any actual intent content rendered?

⚠️ **Do not test this by grepping for a ticket key.** It looks like the obvious check and it
gives a false positive:

```bash
grep -rl "SSPN-" ep-intents/ | wc -l      # 4  — and 4 in the plain run too
```

Those hits are **doc ingestion**, not intents — lines like
`**Documented in**: docs/specs/build-documents/SSPN-49-build.md#3-root-cause`, produced by the
`Doc`/`MENTIONS` tier whether or not `--intents` is passed. Confirm they are unrelated by
checking the files are byte-identical across both runs:

```bash
for f in $(grep -rl "SSPN-" ep-intents/ | sed 's|ep-intents/||'); do
  cmp -s "ep-a/$f" "ep-intents/$f" && echo "IDENTICAL: $f" || echo "DIFFERS: $f"
done
```

Expect **all `IDENTICAL`** ✅. The authoritative check is the tree diff above: two count lines,
nothing else. No page says which ticket a symbol serves — the facts are counted, not shown.

## 7. `--intents` on `state`

```bash
PYTHONHASHSEED=0 $SPINE state spine --no-timestamp > st-plain.md
PYTHONHASHSEED=0 $SPINE state spine --intents --no-timestamp > st-intents.md
diff st-plain.md st-intents.md
```

Observed — **one line**, the size summary:

```
< - Size: 643 namespaces (≈50 areas) · … · 1233 docs
> - Size: 643 namespaces (≈50 areas) · … · 1233 docs · 34 intents
```

Pin `PYTHONHASHSEED=0` on both sides, or §5.1 will add unrelated noise to this diff and you
will misread reordered `scripts/` entries as an intent effect. That is the trap this plan
exists to spare you.

## 8. Can you read the intent facts at all?

If nothing renders them, the natural next step is to export the graph and read them directly.

```bash
$SPINE pkg export --help | grep -ic intent      # 0
$SPINE pkg extract --help | grep -ic intent     # 0
```

Expect **`0` from both**. `--intents` exists only on `understand` and `state`; the two commands
that can emit the graph have no such flag, so they never compute Intent facts. Confirm the
export is empty of them:

```bash
$SPINE pkg export spine --format json -o g.json >/dev/null
python3 -c "
import json; d = json.load(open('g.json'))
print('Intent nodes:', sum(1 for n in d['nodes'] if n.get('kind') == 'Intent'))
print('SERVES edges:', sum(1 for e in d['edges'] if e.get('kind') == 'SERVES'))"
```

Expect ✅:

```
Intent nodes: 0
SERVES edges: 0
```

**Conclusion to record.** The facts are computed in-process, counted into a summary line, and
discarded. There is no supported way to read which ticket serves which symbol. That is the
§4 "facts with no reader" gap in
[`pkg-accuracy-gaps.md`](pkg-accuracy-gaps.md), confirmed at the command line.

## 9. Cost of `--intents`

```bash
time $SPINE understand spine --out /tmp/t1          # warm
time $SPINE understand spine --intents --out /tmp/t2
```

Observed *(repo-dependent, 517 commits)*:

| run | wall | user | system |
|---|---|---|---|
| plain | **13.2s** | 12.6s | 0.4s |
| `--intents` | **16.6s** | 19.0s | 18.1s |

Wall-clock cost is modest (**+3.4s, +26%**) because blame runs at 8 workers — but total CPU
goes from 13.0s to **37.1s, roughly 3×**. The help text's "adds ~8s" is pessimistic on wall
time and silent on CPU. On a shared CI runner the CPU figure is the one that bites.
