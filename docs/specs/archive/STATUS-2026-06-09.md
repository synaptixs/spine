## 1. Executive summary

The orchestrator is a working **AI-native SDLC platform** with three end-to-end
capabilities live against real services: PR review (Block A), Confluence→Jira
backlog generation (Block B), and SDLC orchestration with approval gates
(Block C). The core engine — multi-provider LLM gateway, LangGraph runtime,
Temporal workflows, a verifier chain, approval gates, and an audit/token ledger —
is built and tested (**458 tests passing**).

The strategic gap is **comprehension**: the agents generate and review without a
grounded model of the *existing* system (Gap G1, rated Critical). **Ontomesh**
— an ontology-mining + GraphRAG toolkit — is a strong fit to supply most of that
comprehension layer. The decided architecture: the orchestrator builds a
**repo-code extractor** (the one thing ontomesh doesn't do) and runs **ontomesh
as a sidecar** over shared Postgres, integrated behind a `KnowledgeGraphAdapter`
Protocol via REST/SPARQL. This compresses a planned ~5-month comprehension track
into "build one extractor + wire one adapter."

## 3. Ontomesh — what it is

**Source:** `github.com/synaptixs/ontomesh` (private, Apache-2.0, Python 3.12,
v**3.8.0**, preview — "expect breaking changes until 1.0").
**Tagline:** *"The ontology mesh for GraphRAG. Mine ontologies from your logs,
validate with SHACL, ship a hybrid retriever."*

### 3.1 What it ingests (verified from `integrate.md` + repo tree)

1. **Relational databases** — `toolkit.py --db …` infers an ontology from a DB
   schema, driven by an **annotation control plane** (`ontology_metadata`:
   table→column→`semantic_class` / `business_term` / `sensitivity`). Primary path.
2. **Logs** — Drain3 templates, per-service HMMs, Granger / transfer-entropy
   gating, PMI co-occurrence (the "discovery" features).
3. **Human wizard** — 11-step domain modeling (Domain → Entities → Events →
   Relationships → CQs → Rules), 10 starter industries.

### 3.2 What it produces (the valuable part)

- **OWL 2 / Turtle ontology · SHACL 1.1 shapes · JSON-LD · SKOS**, with
  **PROV-O lineage** (`prov:wasDerivedFrom`).
- **Reasoning:** OWL-RL · SWRL · Datalog (Rulewerk).
- **Hybrid GraphRAG retriever** + **SPARQL** "Ask" console — cited, reasoned
  answers with a materialized result subgraph and a streamed reasoning trace.
- Served from **Postgres or SQLite** over REST: `/api/ontologies`,
  `/api/templates`, SSE drift feed `/api/events/stream`, `/health`.
- Backends: Postgres/MySQL/MSSQL/Oracle/DB2; vector FAISS/Chroma (pgvector +
  Qdrant scaffolded); LLM adapters Anthropic/OpenAI/Vertex/Ollama/OCI.
- Deploy: Docker `ghcr.io/synaptixs/ontomesh:3.8.0` (~316 MB), Compose / Fly.io /
  Render / Cloud Run. 1000+ tests, cosign-signed.

### 3.3 The critical caveat

Ontomesh **as shipped does not parse source code**. Its `src/` is
ontology-engineering modules (`causality_miner`, `alignment_generator`,
`cq_tester`, `conflict_resolver`); inputs are **DB schemas + logs + docs**, not
ASTs. Its strength is the **semantic / ontology / retrieval / validation layer**,
not code structure. This single fact drives the integration design.

## 4. Integration assessment (G1)

### 4.1 Fit against Track 1 (Product Knowledge Graph)

| Track 1 wedge | Owner | Notes |
|---|---|---|
| **1.1 Structural code extractor** (AST, imports, ORM→entities, routes→endpoints, test↔code, `file:line` provenance) | **Orchestrator (we build)** | Ontomesh can't parse code — this is ours |
| **1.2 Doc / semantic layer** (purpose, business rules, glossary, sensitivity) | **Ontomesh** | Annotation control plane + alignment generator |
| **1.3 Retrieval API (GraphRAG)** | **Ontomesh** | Ships a hybrid retriever + SPARQL — delegated |
| **1.4 GroundingVerifier + freshness** | **Ontomesh** | SHACL + PROV-O lineage + SSE drift feed = the grounding/drift verifier |
| **1.5 Formal ontology / OWL growth** | **Ontomesh** | Core competency |

**Net:** ontomesh supplies ~4 of 5 wedges with a mature, 1000-test engine;
the orchestrator owns code-structural extraction, which is also the **bridge** —
code facts get meshed with DB-schema- and log-derived knowledge into one
product-specific KG.

### 4.2 Decided architecture

```
   ┌─────────────────────── orchestrator ───────────────────────┐
   │  RepoCodeExtractor  (NEW — we build this)                   │
   │   AST · imports · ORM models→entities · routes→endpoints    │
   │   · test↔code links · provenance file:line                  │
   │            │ emits facts (rows / JSON-LD)                    │
   │            ▼                                                 │
   │  KnowledgeGraphAdapter  (Protocol — same seam pattern)      │
   │   .ingest_facts(...)        .retrieve(task)→subgraph        │
   └────────────│ REST / SPARQL ──────────────────│─────────────┘
                ▼                                  ▲
   ┌──────────────── ontomesh sidecar (3.8.0, pinned) ──────────┐
   │  meshes code facts + DB schema + logs + docs               │
   │  → OWL ontology · SHACL invariants · GraphRAG · SPARQL     │
   │  shared Postgres  (ONTOMESH_DB_URL → our DB)               │
   └────────────────────────────────────────────────────────────┘
```

**Decisions locked in this session:**
- **Code extraction:** orchestrator builds a "read any existing repo" feature.
- **Coupling:** sidecar via REST/SPARQL (not library import — isolates ontomesh's
  pre-1.0 churn behind the adapter seam).
- **Consumers:** SDLC agents (codegen, reviewer, gap-analyzer) call
  `adapter.retrieve(task)`; **SHACL shapes plug into the verifier chain as the
  GroundingVerifier**.

### 4.3 Open questions to validate before building

1. **Fact-ingestion contract** — cleanest way to push code facts into ontomesh:
   its `ontology_metadata` annotation tables, a direct triples/JSON-LD load, or
   `/api/ontologies`. This contract *is* the integration boundary.
2. **Version pinning** — pin `:3.8.0`; keep the adapter thin so breaking changes
   stay behind the seam.
3. **Shared Postgres topology** — confirm `ONTOMESH_DB_URL` against our DB
   (separate schema vs separate database) and migration ownership.
